The Trading Desk on Lakebase

Build a CIBC Capital Markets coverage desk on Lakebase — managed Postgres on Databricks. 1

Get to know Lakebase

UI walkthrough · no code

Lakebase is fully-managed PostgreSQL (16/17) built into the lakehouse — the OLTP store behind your desk's apps and agents, sitting next to the Delta tables you already query. It autoscales, scales to zero when idle, branches like Git, and syncs with Unity Catalog.

  1. In the workspace, open Compute → Database Instances (a.k.a. Lakebase) and open the shared workshop project. You share it with the room, but you work on your own branch — br · <your-username> — an isolated copy the facilitator created for you.
  2. Open your branch and note its compute endpoint. An IDLE state is normal — the endpoint scaled to zero and wakes on the next connection. (Every exercise connects to this branch automatically.)
  3. Open the built-in SQL Editor against your branch and run these — they work on an empty branch (you'll create tables in Exercise 2):
-- which Postgres, who am I, where do names resolve?
SELECT version();
SELECT current_user, current_database();
SHOW search_path;

-- create your workshop schema (underscores, not hyphens)
CREATE SCHEMA IF NOT EXISTS cm_<you>;
✓ Check — version() returns a PostgreSQL 16/17 banner, current_user is your email, and your cm_<you> schema now exists.

Step 6 — watch your branch autoscale under load

Market open: a burst of pricing/limit queries hits your book. Run Autoscale_Load.py — it fires a concurrent workload at your branch and its compute scales up from the minimum toward its max, then settles back to zero when the load stops. You pay only for what you use.

Heads-up: the notebook polls endpoint state (the live CU number isn't in the API) — open the Lakebase Monitoring graph alongside it to see the CU curve. Your facilitator provisions your branch with room to scale (max > min CU).
✓ Check — compute rises above the minimum while the load runs and settles back afterward (visible on the Monitoring graph).

REST vs JDBC

Applications reach your branch two ways: a stateless REST data API (great for serverless / edge front ends, any language, per-request auth) or a pooled JDBC connection (lowest latency for chatty JVM services). Same data, two access patterns.

Online feature store & the Coverage Desk Assistant

feature serving · MLflow · LangChain

Turn the desk's data into per-client risk features, publish them to Lakebase for low-latency serving, expose them through a Feature Serving endpoint, and build a chatbot whose feature-lookup tool calls that endpoint. The diagram shows what gets spun up and how each piece relates to Lakebase.

⏳ Two long steps (expected, not a hang): publish_table stands up the sync pipeline (~15–20 min the first time) and the Feature Serving endpoint takes ~10–15 min to provision. Both are fixed overhead regardless of data size — kick them off and use the time to talk through the architecture above.
Run the notebook

Run Feature_Store.py first (it creates the endpoint), then Coverage_Desk_Chatbot.py. The heart of it:

fe.create_table(name=FEATURE_TABLE, primary_keys=["client_id"], df=features)
# enable CDF, then publish into your Lakebase project
fe.publish_table(online_store=fe.get_online_store(name=PROJECT_ID),
                 source_table_name=FEATURE_TABLE, online_table_name=ONLINE_TABLE)
fe.create_feature_spec(name=FEATURE_SPEC,
     features=[FeatureLookup(table_name=FEATURE_TABLE, lookup_key="client_id")])
w.serving_endpoints.create_and_wait(name=EP, config=EndpointCoreConfigInput(
     name=EP,   # required by the SDK — omitting it errors
     served_entities=[ServedEntityInput(entity_name=FEATURE_SPEC,
         workload_size="Small", scale_to_zero_enabled=True)]))

The chatbot's tool is the exact lookup — an MLflow call the LLM decides when to make:

@tool
def lookup_client_risk(client: str) -> str:
    """Live risk features (exposure, PnL, volatility, risk tier)."""
    return get_deploy_client("databricks").predict(endpoint=EP,
        inputs={"dataframe_records":[{"client_id": resolve(client)}]})

Give the assistant a memory

LangGraph · PostgresSaver · Lakebase

The assistant currently forgets each turn. Back it with a LangGraph PostgresSaver checkpointer pointed at Lakebase, and its conversation state becomes durable — surviving turns, new processes, and sessions — because the memory lives in Postgres, not the process. The diagram shows where that memory sits.

Run the notebook

Run labs/05-agentic-memory/Agent_Memory.py. Two Lakebase gotchas are baked in — connect with keyword args (not a URL), and subclass ChatDatabricks to drop temperature (Claude endpoints reject it):

conn = psycopg.connect(host=host, dbname="databricks_postgres",
    user=user_email, password=cred.token, sslmode="require",
    autocommit=True, options=f"-c search_path={PG_SCHEMA},public")
checkpointer = PostgresSaver(conn); checkpointer.setup()   # makes the 4 tables
agent = StateGraph(MessagesState)...compile(checkpointer=checkpointer)

Lakebase → Delta (SCD Type 1 pipeline)

CDC · Lakeflow · SCD1

The round trip: the trading app mutates operational tables all day; the lakehouse needs the current picture for risk analytics. Turn on Lakebase Change Data Feed — it auto-materializes every change into lb_*_history Delta tables — then a Lakeflow (DLT) AUTO CDC flow applies SCD Type 1 (latest value wins, no history).

Public Preview: Lakebase CDF requires REPLICA IDENTITY FULL on the source tables (the notebook sets it), a destination catalog that doesn't use default storage, and CAN MANAGE on the project to create the feed. Deletes are captured natively (_pg_change_type='delete'). If the create step is denied, ask your facilitator.
Run the notebook + pipeline

Run labs/07-lakebase-cdf-to-scd1/Lakebase_CDF_To_SCD1.py (seeds + mutates positions/limits, enables CDF, then creates the Lakeflow pipeline from scd1_pipeline.py) and confirm each key shows only its latest value.

pgvector · embeddings · agent
