Facilitator setup guide

Prep the room before the desk opens

Everything you run before attendees arrive: stand up one shared Lakebase project, give every attendee their own isolated branch, grant access, and (if the room is large) split across extra projects. One notebook does the heavy lifting — run entirely in Databricks, no CLI.

Setup time · ~15 min + branch provisioning You need · workspace admin Notebook · scripts/facilitator_setup_notebook
◆

The model: one project, a branch per attendee

All attendees share one Lakebase project, but each works on their own branch — a Git-like, copy-on-write, fully-isolated clone of the project with its own compute endpoint. The exercises connect to the attendee's own branch automatically (labs/_setup.py derives the branch id from their username). Nobody steps on anyone else's data, and each person can freely create, load, and even break things on their branch.

Isolation is by branch, enforced by convention. Lakebase access control is at the project level (attendees get CAN_USE on the project), so technically an attendee could point at another's branch — but the exercises always resolve their own branch, so in practice each person stays in their own sandbox. Good enough for a workshop.

Run the setup notebook

Open scripts/facilitator_setup_notebook and Run all to render the widgets. It creates the shared project, grants your attendees, and forks a branch (with its own endpoint) for each — all with your notebook identity, no CLI. Fill the widgets:

# widget                     value
grant_users                = sofia.martins@cibc.com, david.chen@cibc.com, priya.nair@cibc.com
project_id                 = cibc-cm-workshop
uc_catalog                 = main
branch_max_cu              = 4
dry_run                    = true   # preview first, then set false and re-run
# warehouse_id           = <id>   # OPTIONAL — the workshop needs no warehouse

What it does — all idempotent, safe to re-run:

  1. Creates the project cibc-cm-workshop (if missing) and waits for its production endpoint.
  2. Grants each attendee CAN_USE on the project and creates their Postgres OAuth login role (installs the databricks_auth extension).
  3. Forks a branch per attendee off production (br · <username>, no_expiry) with a primary READ/WRITE endpoint set to an autoscaling range of 1 → 4 CU (from branch_max_cu) so the Exercise 1 load demo can show compute scaling.
  4. Creates the UC catalog + a per-attendee cm_<user> schema they own + USE CATALOG (uc_catalog widget). (The Claude endpoint is a system foundation model — no CAN QUERY grant needed.)
  5. Prints the attendee → project/branch map, the workspace toggles to confirm, and the one value each attendee sets.
Why branch_max_cu = 4: Exercise 1's autoscale/load demo only shows a curve if the branch endpoint can scale (max_cu > min_cu). Without it, branches sit at 1 → 1 CU and the graph is flat. The SDK reports endpoint state and the min/max envelope but not a live CU number — confirm the range in the Lakebase UI (branch → endpoint → compute) if needed.
Tip: keep dry_run = true first to see exactly what it will do without changing anything, then set it false and re-run. Set the app_name widget if you're also deploying a Lab app (grants its service principal a role).
✓ Check — the notebook prints one br · <username> per attendee with "branch created" + "endpoint"; the map lists every attendee against the project.

Then confirm the workspace toggles (not per-user grants)

The notebook sets the per-user grants — the Lakebase project and the UC catalog/schema. What's left isn't a grant at all; it's workspace-level enablement the notebook reminds you to confirm:

  1. Serverless notebooks/jobs enabled. The exercises run on serverless notebook compute — no SQL warehouse needed.
  2. Model Serving + Foundation Model APIs enabled in the workspace/region. The Claude endpoint is a system foundation model — workspace users query it with no per-user grant.
  3. Serverless DLT enabled. Attendees create the Ex7 pipeline and the Ex4 Feature Serving endpoint with their workspace access — there's no distinct "create pipeline"/"create endpoint" entitlement to grant.

Point attendees at the project + catalog

Attendees set two values — the SHARED_PROJECT_ID and SHARED_CATALOG constants in labs/_setup.py — to the project id and Unity Catalog catalog you created. Set once, every exercise inherits them (nothing to configure per notebook). Their branch and their cm_<user> schema are derived from their username automatically — nothing else to set:

# each attendee, once, in their clone of labs/_setup.py:
SHARED_PROJECT_ID = "cibc-cm-workshop"
SHARED_CATALOG    = "main"   # the catalog you passed to the setup notebook
Fail-fast & auto-routing: if the project id is unset or wrong, the exercises stop immediately with a clear message (no 10-minute hang on a nonexistent project). And if you split a large room across projects (below), attendees can still set the base id — _setup finds whichever split project holds their branch and uses it.
＋

Optional: too many attendees for one project

A Lakebase project caps how many branches it can hold. If your headcount would exceed it, cap the branches per project and the notebook automatically creates additional projects (cibc-cm-workshop-1, -2, …) and splits attendees across them — just set the max_branches_per_project widget:

# widget
project_id                 = cibc-cm-workshop
grant_users                = a@cibc.com, b@cibc.com, ...
max_branches_per_project   = 18
uc_catalog                 = main
What changes for attendees: nothing, really — they can all set the base id (SHARED_PROJECT_ID = "cibc-cm-workshop") and _setup auto-routes each person to the split project that holds their branch. (Setting the exact project from the printed map, e.g. cibc-cm-workshop-2, also works and skips the lookup.)

Set max_branches_per_project a little below your workspace's actual limit to leave headroom. Re-running is safe: existing projects/branches are detected and skipped.

Run of show & the long waits

Suggested full-day flow (~6–6.5h, or split at the break into two half-days) — the recommended order is 1 → 7:

  1. 1 · Getting to know Lakebase (45m) — orientation + the SQL Editor, then the autoscale/load demo.
  2. 2 · Authentication + data (45m) — connect from Python; generate the CM dataset; VS Code.
  3. 3 · Data APIs — REST vs JDBC (30m) — two ways an app reaches the branch.
  4. — break (10m) —
  5. 4 · Online feature store + chatbot (75m) — the money shot; two long waits (below).
  6. 5 · Agentic memory (45m) — persistent memory with LangGraph + Lakebase.
  7. — lunch / long break (30–45m) —
  8. 6 · Delta → Lakebase sync (30m) — reverse-ETL a Delta table into an lb_* synced table.
  9. 7 · Lakebase → Delta, SCD Type 1 (40m) — capture lb_* changes; Lakeflow AUTO CDC.
  10. Wrap (15m).

Tight on time? The core arc is 1 → 2 → 4 → 5; exercises 3, 6 and 7 are self-contained and can be dropped or run as a shorter integration half-day. The full talk track, the hero thread (Air Canada's energy exposure), and honest talking points are in FACILITATOR.md.

Two steps in the feature-store exercise (4) run long — this is expected, not a hang. publish_table stands up a serverless sync pipeline into Lakebase (~15–20 min the first time) and the Feature Serving endpoint takes ~10–15 min to provision. Both are fixed overhead regardless of data size — use the time to walk the architecture diagrams in the attendee guide. (The Delta→Lakebase sync (4) and the SCD1 pipeline (5) also provision, but only a few minutes each.)

Optional pre-warm

To remove the publish wait for attendees, run the feature-store Feature_Store notebook once yourself before the room. Attendees then hit a fast incremental re-publish against the existing pipeline instead of the cold provision. (Serverless is not the lever — the sync is already serverless; pre-warming is what skips the cost.)

4

Cleanup after the workshop

Branches are created with no_expiry, so they persist until you remove them. After the session:

  1. Attendee branches: delete each br · <username> (Lakebase UI → project → Branches, or w.postgres.delete_branch(...)). This frees the branch count and its endpoint, and clears everything on it — the cm_<user>, lb_*, and checkpoint% tables.
  2. Sync + SCD1 artifacts (Ex6/Ex7): delete each synced table (removes its sync pipeline) and the Lakeflow/DLT pipeline; optionally drop each attendee's cm_<user> UC schema (it holds the feature-store, sync, and SCD1 tables).
  3. Feature-store artifacts: delete each Feature Serving endpoint (w.serving_endpoints.delete) and online table (w.feature_store.delete_online_table — never DROP TABLE, which orphans data).
  4. Projects: stop or delete the shared project(s) — Lakebase does not auto-stop, so stop it if idle cost matters.
Reset an attendee mid-workshop: delete their branch and re-run the setup script — it recreates just the missing branch.
